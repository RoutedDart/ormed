# Queries

Ormed has a few ways to reach the database because a list screen, a model mutation, and a transaction have different responsibilities. Pick the smallest layer that matches the job, then move to a lower layer when you need more control.

## Pick an API by the job

| If you need to... | Use | Why |
| --- | --- | --- |
| Compose filters, joins, projections, or aggregates | [Query Builder](./query-builder) | Controls the shape of a typed read or write without hiding the SQL work |
| Insert, update, delete, or upsert a model | [Repository](./repository) | Keeps model-centric mutations and persistence rules together |
| Initialize connections, run transactions, or route databases | [DataSource](./data-source) | Owns connection lifecycle and the boundary around multiple operations |
| Explore a table or run SQL before you have a model | [Direct Database Access](../getting-started/direct-database) | Lets you start with the schema and add generated models when they become useful |

For a multi-step change, put the read and write operations inside a [transaction](./data-source#transactions) so they succeed or fail together. Keep connection setup in the `DataSource`; keep filtering and projections close to the query that needs them.

## Choose a starting path

- **Listing, searching, or reporting:** start with the [Query Builder](./query-builder). Add joins, predicates, ordering, pagination, or projections as the screen requires.
- **CRUD around a model:** start with the [Repository](./repository). It is the clearest home for create, update, delete, and model-oriented workflows.
- **Boot, transactions, or multiple databases:** start with [DataSource](./data-source), then call the query or repository API inside that lifecycle boundary.
- **No stable model yet:** use [Direct Database Access](../getting-started/direct-database) while you learn the schema. Introduce a generated model when repeated access benefits from types and shared behavior.

## Learn in this order

1. [Query Builder](./query-builder): core read/write fluency.
2. [Repository](./repository): structured model mutations.
3. [Loading Relations](./relations): association-aware reads.
4. [DataSource](./data-source): boot, connection control, transactions.
5. [JSON Queries](./json) + [Caching](./caching): specialized tuning.

## Keep the boundaries clear

The query builder controls SQL shape. The repository controls model workflow. The `DataSource` controls connection lifecycle and transaction scope. Keeping those responsibilities separate makes it easier to test a query, change persistence behavior, or add another database without rewriting every call site.
